## What this repo is

Two fused lineages share one monorepo. The **live** one is the **agent harness**: retrieve a plan by topology, realise its geometry from a graph, judge it with sensors, and repair it with moves — all wrapping a locked deterministic core (design: workspace `docs/agent-harness-build-plan.md`). The **second**, `packages/floor_plate_design`, is the DfMA floor-plate generator + compliance checker (national-housing-program-adjacent); it dominates the repo by edge count but is not the harness. Harness work lives in `packages/floorplan_core`. The two are not fully separate: they meet at the **plate → unit handoff**. The plate generator subdivides a floor plate and hands each unit down as a *boundary + typed edges (`external` / `facing_corridor` / `shared_wall`) + a north bearing* (site orientation). That handoff is the unit harness's input — the unit harness never invents a unit's exposure or orientation, it receives them. The **facade-exposure typology** (below) is the shared vocabulary across the handoff, and the sensor/move/objective pattern is expected to recur at the plate level (a plate harness) when subdivision work resumes.

## The data structure everything hangs on — the plan / unit dict (v2.1.0)

`boundary` [[x,y],…] · `rooms` [{id, type/label, polygon}] · `edges` [{u,v,connection}] (room↔room adjacency) · `entrance` [x0,y0,x1,y1] · `windows`/`doors` · `retrieval` {dist, mirror, topo{…}} · and the **derived topology layer**: `room_edges` (room↔boundary, raycast), `node_pos` (room node in target frame), `flags` (sensor results). Retrieved vs derived vs editable matters: room↔room edges are retrieved, then reconciled after a move (see The two topologies); room↔boundary (`room_edges`/`node_pos`) is derived by `topo_signature`; the agent will edit only the spec, never geometry.

## The two topologies

**room↔room** — from the plan's `edges` (adjacency/door graph); at retrieval, `filter_corner_adjacencies` (topo_signature) drops any source edge whose two room polygons meet only at a corner (shared boundary length ≤ tol) — a point contact is not an adjacency, so it never enters the drawn graph, generation, or reachability. Fixed at retrieval, but **reconciled after any move** (`reconcile_edges` in `rectangular_arrange`, applied by both `swap` and `generate`): connections (door/open) follow room identity where still realised-adjacent, walls are re-derived from the realised geometry, and a connection whose rooms no longer touch is reported as a **dropped connection** — so a move never leaves stale identity-keyed edges for the drawn graph or the sensors to read. **room↔boundary** — derived geometrically by raycast in `topo_signature` (`_raycast_room_edges`), never from the dataset's window annotations. For each exterior wall a ray is cast from the **room node** (robust: a node-origin ray reaches an edge even on a non-convex boundary) to find the target edge; the contact is kept only if (a) the wall's placed midpoint is within **PROX_TOL** of that edge — a *proximity* test that keeps a genuine contact whose ray crosses a neighbour (LR→corridor with the bathroom in between) while dropping a phantom whose wall sits deep interior (bathroom→north) — and (b) its realised width clears the **edge-type floor**: `WINDOW_MIN_WIDTH_M` 0.8 m on `external` edges (a window; project choice 2026-10-30, below the BADS 1.2 m) or `DOOR_MIN_M` 0.9 m on `facing_corridor` edges (a door). Each contact carries `width_m`; the daylight sensor (D26) tests that physical width, not a fraction. The daylight/access/capacity sensors read both derived layers, so these guards correct the scores as well as the drawing.

**room↔boundary on generated geometry (closed 2026-10-29; exact since 2026-10-30).** `room_edges` was computed on the *retrieved* plan and reused for `/generate`, but the node-driven solver re-tiles the boundary, so which room fronts an edge changes (a room drawn off the corridor still carried the source's corridor contact — the LR→west phantom). `/generate` now re-derives `room_edges` from the generated polygons via `_raycast_room_edges(..., in_target_space=True)`: the polygons and nodes are already in target space, so the display transform is identity and the plan's own boundary is the target. The same proximity test + edge-type width floor apply. Both the drawn overlay and the Stage-1 sensors now read realised frontage. **Since 2026-10-30 `/generate` uses `exact_room_edges` instead of the raycast:** generated rooms already sit in the target, so a contact is a room wall lying along a boundary edge — overlap intervals merged per edge, `width_m` = the widest run. The raycast kept one hit per ray and lost contacts (a living room fronting a 2.6 m window was reported on its 1.6 m one). `/retrieve` and `/topo_check` keep the raycast (`in_target_space=False`). Same output shape, same floors.

## Main action, end to end

Draw boundary+entrance+requirements → `/retrieve` → `run_retrieval` (npz search → pool of 60 → `topological_fitness` re-rank, attaches `node_pos`+`room_edges`) → winner drawn as a topology graph → `/topo_check` (`topo_sensors.run_sensors`) → select two nodes → `/swap_nodes` (`swap` → `rectangular_arrange.arrange` re-realises geometry) → re-check sensors.

## Agent harness — the live build (Stages 0–1 built; Stage 2 started)

The forward design (workspace `docs/agent-harness-build-plan.md`): a fixed Observe → propose → rollout → select → escalate loop over two open registries (Sensors, Moves) with fixed contracts, wrapping a **locked Generator**.

**Stage 1 — BUILT (2026-10-26):** `packages/floorplan_core/topo_sensors.py` migrated to the sensor contract — each sensor has `kind: hard|soft` and `evaluate→{ok, failing_rooms, margin}`; `run_sensors` returns `{summary{passed, total, gates_pass, soft_score}, checks}`. Eight sensors: reachability / access_typed / entrance_valid (topology, hard), **daylight (D26), room_depth (D25), min_room_size (D24)**, boundary_capacity (geometric, hard), node_in_room (soft). Daylight and depth are judged per **open-plan component** (connected components over `open` edges): an unlit non-private room passes only when open-connected to a lit one — the compliant form of borrowed light, the open/closed-kitchen decision. **An edge is open only when it says so** (`separation: open` or `connection: 2`); the earlier inference that a door between two common rooms is open plan was dropped 2026-10-30 (it let a windowless kitchen borrow light through a door and measured depth across doors). Edges carry `connection` 0 wall / 1 door / 2 open, plus an authoritative `separation` written by SetConnection; open edges are passable. **Layers (2026-10-30):** `run_sensors(layer=)` — `"topology"` (retrieved plan: `/retrieve` flags, `/topo_check`) skips `GEOMETRIC_SENSORS` (room_depth, min_room_size, node_in_room), whose polygons are still the source plan's; `"geometry"` (generated plan) skips `TOPOLOGY_ONLY_SENSORS` (boundary_capacity — a pre-geometry feasibility question that pinned each daylight room's min width to one edge). **D24 (2026-10-30)** measures the usable footprint, not the bbox: core = a `min_edge` square must fit; area = the room's usable area (reachable by a `USABLE_WIDTH_MM` 900 square) must meet `min_area`; reports pinched rooms and area below min width. **D25 (2026-10-30)** is wall by wall: a wall opposes a window when parallel and facing it; its depth is the distance to its nearest opposing window; every such wall must be within the limit; walls on a window line are skipped (dual aspect). Thresholds are grounded in the workspace doc `projects/project-44/docs/bads-sensor-model.md` (Better Apartment Design Standards, Victoria). Scored on real `/generate` output and shown in the in-app "stage 1 · sensors" panel. The sensors run on generated geometry, so `topo_signature._label` now **canonicalizes** label spellings (int / `"LivingRoom"` / `"living_room"`) to the category vocabulary — without it, generated-plan rooms mis-classified silently. Sensor `detail` strings name rooms one way, `r_2 (kitchen)` (`_nm`/`_nms`); `failing_rooms` stays bare ids. `access_typed` stays strict (doors, not adjacency) and returns `door_candidates` `[[room, provider]]` — wall-adjacent transit rooms with a shared wall ≥ 0.9 m — the exact-effect input for SetConnection (2026-10-30).

**Stage 0 — BUILT (2026-10-24):** `packages/floorplan_core/generate.py` carries the `Spec`/`Plan` seam (`spec_from_plan`, `generate`, `reassign`) and the node-driven solver — room polygons from node positions + boundary: node-seeded grid → **containing-cell seeding** + nearest-node fill → **boundary-contact repair (step 2b)** → **area-weighted re-dimension** (each room sized toward its source `area_frac`, a D1 dimensional demand) → clip → **thin-arm carve (step 4b)**. Replaces `arrange()`'s cell-from-source-bbox grid. **Step 2b (added 2026-10-29) makes topology drive geometry:** the Spec carries `boundary_demands` (`{room_id: [target_edge_index]}` — which target edge each room should front, from the topo-rank ring alignment, threaded in by `/generate`), and `_repair_boundary_contacts` transfers border cells so a room reaches a demanded edge it would not own by node proximity alone (the LR→west case: LR's node is central, so the west column goes to the bathroom; 2b gives LR a contiguous west cell). A transfer commits only if every donor stays non-empty, 4-connected, and keeps its own fronts; it tries candidate edge cells shortest-first and commits the first valid one. **Step 4b (added 2026-10-29) catches what a whole-cell transfer cannot:** when the demanded edge is over-subscribed and the room is interior (the LR→west case — four rooms want the west side, the column holds three), `_carve_arm` gives the room a **thin L-shaped arm** reaching the edge, carved from the rooms it crosses (the source's thin reach a rectangular partition can't make). The arm width clears the edge's door/window floor (`×1.05`); a carve commits only if every donor stays non-empty, single-piece, and keeps its own demanded fronts. Satisfied-by-arm demands move to `report.boundary_contacts.arms`. The guarantee is conditional — a demand with no feasible transfer or carve is reported in `report.boundary_contacts.unmet`, not forced. Exposed at `/generate`; in-app visual test is the "stage 0 · generate from nodes" sidebar panel (generate / generate+swap / reset), redrawing the generated rooms over the topology nodes. Known limits, reported not hidden: on a **non-convex (notched) boundary** a node's grid column can cross the notch, so the clipped room may not contain its node — `report.node_relocated` counts these and the display marker is moved to the room interior; and exact per-room areas can't be hit on a shared grid (`ncol+nrow` DOF < n rooms), so `report.area_mae` measures the residual (~2% on convex, ~6% with notches). Min room size remains a Stage-1 sensor. A true Voronoi realiser would guarantee node-in-cell but at the cost of non-rectangular rooms (deferred). ARAP is retired as the realiser. Next: Stage 1 (sensor interface + min-size + the facade-exposure context of §6b). Requirement held: every stage gets an in-app visual test (extend the topology-graph canvas + sensor-flags panel). **Min sizes (2026-10-30):** `spec_from_plan` labels rooms via `topo_signature._label` (canonical), so `MINIMUM_SIZES`/`FLEX` resolve; `/generate` defaults `mm_per_unit` to `SCALE` (the frontend does not send it). Before this, step 3 enforced no minimum. `report.rooms` carries area provenance — `area_rect` (after step 3, before clip), `area_clip`, `arm_donor_to` — and `_carve_arm` returns its donors. **Notch-aligned grid (2026-10-30):** step 1 pins the boundary's vertex coordinates as grid lines (`_grid_lines(..., fixed=)`); cells whose centre lies outside the boundary get no owner, and step 3 (`_solve_positions(..., fixed=)`) keeps pinned lines in place and moves only the node cuts, so on an orthogonal boundary the clip removes nothing. `PIN_MIN_SEG_FACTOR` (default 0.0 = pin every vertex) can skip short jogs; measured worse. `report.grid_lines` {xs, ys, pinned_x, pinned_y, cells[i, j, owner|None]} feeds the canvas grid drawn under the generated rooms. **`min_area` lift (2026-10-30):** after a feasible step-3 solve, the worst-off room's per-axis minimum is raised (both axes ×√f, else one axis ×f) and re-solved; a trial is kept only if both axes stay feasible, the room's aspect stays ≤ `ASPECT_MAX` 2.5 (or its prior ratio), and no room that met `min_area` falls below it. Reported in `debug_steps[3_resolve]` (`area_lifted`, `area_unmet`) and `report.rooms[].area_lift`; `spec["area_lift"]=False` turns it off (the app toggle). Known limits: the lift targets cell area, which counts arms the usable-footprint D24 does not; non-orthogonal edges still clip.

**Stage 2 — STARTED (2026-10-30):** `packages/floorplan_core/moves.py` holds the move contract — `applicable(plan, sensors)`, `propose(plan, sensors, ctx_inputs)`, `predict_effect(plan, edit, ctx_inputs)`, `apply(spec, edit)` (pure) — and the `MOVES` registry. **SetConnection** edits one Spec edge to wall/door/open. Guards: rooms realised-adjacent; door needs a shared wall ≥ 0.9 m; open never touches a private room (bedrooms, bathroom). Proposals: doors from `access_typed.door_candidates` and unreachable rooms; open for daylight failures only (depth is geometric — merging adds floor behind the same window). `predict_effect` is exact (geometry unchanged: edit the edge, re-run the sensors); `tools/gate_set_connection.py` confirms predicted = apply + regenerate on 13/13 candidates over `001b`/`005b` top 3. In-app: the "stage 2 · moves" panel (propose → click to apply and regenerate; undo/clear), each candidate labelled with rooms fixed and broken per sensor. Swap is not yet on the contract.
